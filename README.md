# Zelfregiekompas Research Lab

A complete local research workspace for selecting and generating student reflection questions. React/TypeScript + FastAPI + SQLite, with Ollama behind a provider interface. There is no assumed winning method, prevalidated question bank, or claim of educational effectiveness.

The app stores real records and runs experiments in a durable background queue. It does not simulate model results. Demonstration scenarios and starter questions are manually constructed synthetic suggestions, awaiting human review. Only tests use provider doubles.

## Local model setup

Install [Ollama](https://ollama.com/download) on the computer that will run inference. Keep cloud features disabled: set `OLLAMA_NO_CLOUD=1` in the environment of the Ollama server, then restart Ollama. See the [official local-only configuration](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features). Start `ollama serve` if the desktop Ollama application is not already serving requests. Start this backend as described above and open **Models**.

For backend and Ollama on the **same computer**, the default address is `http://127.0.0.1:11434`. On Models, edit the address, click **Save connection**, then **Test connection**. The address is stored in the workspace SQLite database. `OLLAMA_URL` in the backend environment overrides that saved address at startup; remove it to retain UI configuration after restart. A connection test checks Ollama's version endpoint; the separate inference test checks whether an installed model can actually generate text.

Click **Add model** to open the searchable catalog dialog. Search by name or use the family, generation/version, reported-parameter and quantization filters. Select a complete variant, inspect its metadata/source/freshness, click **Use this variant**, then explicitly click **Install**. Search and selection never download weights. Escape closes the dialog and returns focus to Add model; keyboard focus remains inside the open dialog. Models outside the catalog remain accessible under **Advanced / install by exact tag**. That path requires an exact tag, including `:latest` if deliberately chosen.

Install is the only application action that calls `/api/pull`; discovery, catalog browsing/refresh, connection testing and inference never install/update weights. Install shows Ollama's streamed phases and per-layer byte progress, then verifies the exact installed name/locality. Registry, disk, connection and verification errors are displayed. An interrupted pull may leave cached partial layers; explicitly retry Install to resume. Leaving Models keeps an active installation visible when you return; closing the browser disconnects progress, so refresh discovery before retrying.

Installed models refresh every 15 seconds, on browser focus, after connection changes and after installation. The table shows full digest, reported parameter size and quantization, and on-disk bytes expressed in GiB (not RAM/VRAM usage). The scenario-generation, scenario-revision, RAG, constrained-LLM and independent AI-evaluator selectors all use this shared discovery list. Fixed-bank experiments with AI control off do not contact Ollama.

**Test inference** uses its own fixed prompt (`Reply with only: OK`), output budget 16, context 2048, temperature 0, non-streaming JSON and a 60-second generation limit. It explicitly sends `think: false` when `/api/show` reports that supported control. Unverified thinking controls are rejected with an actionable compatibility error; named-level-only models retain supported controls. No retry silently changes controls/models. Success shows response text, elapsed application wall time and available load/prompt/generation timings. Failures distinguish connection, load, timeout, malformed response, empty output, busy, unavailable model and other provider errors, with Ollama HTTP status where available. Diagnostic details include the address, effective settings, stop reason and thinking-character count. Tracebacks and underlying error details are logged on the backend; fixed-test response excerpts are retained, while research prompt/response bodies are not logged by this diagnostic path.

The October 26 diagnosis reproduced an HTTP-200 thinking-only completion from `qwen3:0.6b`: its default thinking consumed all 32 tokens and stopped with `done_reason: length`, leaving no answer. The old test mapped this to generic `provider_error`. Disabling thinking for this short test returns `OK` through the actual application endpoint. The earlier reported 60-second timeout was not reproduced and its historical cause remains unknown. Streaming parsing, locality checks and busy guards were inspected; none caused the reproduced empty answer. See `docs/inference-diagnosis-before.json`, `docs/local-inference-live.json` and `docs/VERIFICATION.md` for evidence.

Research experiments retain streaming and their 128-token/120-second defaults. New UI configurations explicitly use `think:false`; the API retains `null` as a recorded model-default request but blocks it for hybrid models in short-reflection mode. Installed artifact controls and `general.finetune`/version determine compatibility, not a Qwen family/size label. Short mode blocks thinking-only artifacts and unverified thinking controls. Intentional **Thinking experiment** mode requires a supported explicit control, ≥1024 output tokens and `num_ctx >= num_predict + 1024`; up to 65536 output tokens can be deliberately configured. Thinking-2507 may require much larger budgets ([official model guidance](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)); the minimum is not a completion guarantee. No settings/model are changed automatically. Requested settings, controls, effective payload, finish reasons, counts, timings and final-answer diagnostics are retained. Internal thinking is counted separately and never accepted as the final question.

Use **Run research preflight** in Experiments for one representative scenario per selected method/model, using the actual research provider/request/validation path (and evaluator when enabled). Results and failed-request diagnostics are stored outside research outputs and timing aggregates. Batches over ten model-using cases require a passing preflight matching exact settings, snapshots, digests, local connection and implementation versions. Change any of those and preflight again. One successful preflight is not a guarantee of quality or later completion.

### Catalog source, cache and maintenance

The [documented Ollama endpoint index](https://docs.ollama.com/llms.txt) exposes installed-model discovery (`/api/tags`), not a documented downloadable-model catalog. The picker therefore uses a **curated scope of 13 verified exact tags**, covering Qwen 2.5/3, Llama 3.2 and Gemma 3. It is not exhaustive and makes no model-quality or hardware-compatibility recommendation. `backend/catalog_manifest.json` declares each reviewed tag, family/generation and known capabilities. Entries never combine independent size/quantization controls to invent tags. The separately selectable [qwen3:4b-instruct](https://ollama.com/library/qwen3:4b-instruct) entry was verified as reported 4.02B, Q4_K_M, rounded 2.5GB; [Qwen's Instruct-2507 card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) and the public artifact/template were checked. Installation/switching still requires explicit action; this update did not install it. The installed `qwen3:4b` in the pilot is Thinking-2507, not that instruct artifact. [Ollama's thinking controls](https://docs.ollama.com/capabilities/thinking) and the installed `/api/show` values remain authoritative for local requests.

Each exact [Ollama Library page](https://ollama.com/library/qwen3:0.6b) supplies its reported parameter count, quantization, rounded download/disk size and public artifact prefix from the Details section. Counts are never guessed from names: for example, `qwen3:0.6b` reports **752M** on the public page while the local provider reports **751.63M**. Model generation, reported parameters, quantization, public source prefix and the installed full digest are separate fields. Public sizes are rounded decimal units, not predicted RAM/VRAM requirements. Tags and metadata can change; installed-job digest checks remain authoritative for actual runs.

`backend/catalog_snapshot.json` bundles metadata checked on 26 October 2026 for first-launch offline browsing. **Refresh catalog metadata** explicitly rechecks only the manifest's fixed public HTTPS pages and stores the result in SQLite; each entry displays its own retrieval timestamp. No background public fetch occurs. Catalog retrieval sends only public tag URLs, never prompts, scenarios or research records, and does not call Ollama. Browsing cached entries works without internet; installing weights requires internet from the Ollama server.

This is HTML scraping of public exact-tag pages, **not an official catalog API**. Markup may change. The parser verifies the exact tag and expected Details structure; source/layout failures preserve cached entries and their original timestamps, report per-entry errors and do not imply fresh metadata. Filters operate on these actual cached entries, including Unknown when metadata is absent. For a fresh process the persisted SQLite cache is reused.

To extend scope, review an exact local variant on its official page, add that complete entry and capability annotations to `backend/catalog_manifest.json`, then from the repository root run:

```powershell
& '.\.venv\Scripts\python.exe' -m scripts.refresh_catalog
```

This fetches metadata only and replaces the distributable snapshot only if all declared sources verify successfully. Review the resulting snapshot and tests; it never installs weights. The UI refresh updates metadata for existing manifest entries rather than discovering arbitrary new families.

Every new model-using job pins the exact selected names, digests, available metadata and backend Ollama address when queued. Before inference, the app checks the pinned digest and address; resumed jobs retain these identities. A changed/missing model produces an explicit error, never a substitute or implicit update. The provider also checks the digest before and after inference, discarding a result if it changed. Installing an existing tag is an explicit update action and may change its digest. Connection changes and installation are blocked during active research jobs/inference. Avoid modifying Ollama's models outside the app during a run. Old model jobs without pinned metadata must be recreated. The application retains identities, not a copy of model weights: retain weights separately for reproducibility.

All browser application API requests go to `/api` on the research backend; only the backend talks to Ollama or fetches catalog metadata. Source links open the public Ollama website only when clicked. HTTP origins on loopback and `host.docker.internal` are accepted by default. For another local Docker service hostname or a private host IP, explicitly allow it with the backend environment variable `OLLAMA_ALLOWED_HOSTS` (comma-separated exact hostnames/IPs, no schemes or ports). Configure only a trusted local Ollama server. Environment proxies and redirects are disabled. `/api/tags` discovers installed models, `/api/show` checks locality, and `/api/generate` handles inference. Models reporting remote targets, names containing `cloud`, or unverifiable locality are excluded. Do not configure a proxy or allowed hostname that forwards prompts externally.

### Backend in Docker

`127.0.0.1` inside a container refers to that container. For Ollama running on the Docker host, set the backend address to `http://host.docker.internal:11434` in Models, or set `OLLAMA_URL=http://host.docker.internal:11434` in the backend container environment. Docker Desktop provides that hostname. With Docker Engine on Linux, add `--add-host=host.docker.internal:host-gateway` to the backend container (Compose: `extra_hosts: ["host.docker.internal:host-gateway"]`). See [Docker host networking guidance](https://docs.docker.com/desktop/features/networking/#i-want-to-connect-from-a-container-to-a-service-on-the-host).

Ollama must listen on an interface reachable from the container: configure `OLLAMA_HOST=0.0.0.0:11434` and `OLLAMA_NO_CLOUD=1` in the **Ollama server's** environment, then restart it. Limit access with the host firewall to your container network; Ollama is not an authenticated public service. No Ollama CORS changes are needed because the browser never calls Ollama. If both services run on the same local Docker network, use e.g. `OLLAMA_ALLOWED_HOSTS=ollama` and `OLLAMA_URL=http://ollama:11434` in the backend, where `ollama` is the Ollama container's service name; the inference server must also have `OLLAMA_NO_CLOUD=1`.

Run Uvicorn with `--host 0.0.0.0 --port 8000` **inside** the backend container, publish only to loopback with `-p 127.0.0.1:8000:8000`, and access the app at `http://127.0.0.1:8000` so the existing Host/Origin protections apply. Persist/mount the SQLite data directory and Ollama model storage. These are connection instructions for an existing Python/Node image; this repository does not supply a Docker image.

**Remote development:** localhost in SSH, Codespaces, a remote VM, or a remote container refers to that environment, not the user's computer. Changing a browser URL or forwarding the app's port does not make the remote backend able to reach the user's Ollama. For this local-only workflow, run the backend and Ollama on your own computer or its local Docker environment. Cloud inference and cloud-model aliases are unsupported.

Provider-reported name, digest, quantization, parameter-size text, capabilities and available model metadata are retained with runs. If size is absent, it stays unknown. Manually enter parameter count **with provenance** under Protocol & records. Parameter counts are not inferred from model names. Fixed-bank runs display **Not applicable** and do not call a model unless optional AI evaluation is separately enabled.

Official API references: [Ollama generation](https://docs.ollama.com/api/generate), [installed models](https://docs.ollama.com/api/tags), [model installation](https://docs.ollama.com/api/pull). API availability and option support depend on your local Ollama version.

## Core research workflow

1. Enter a pseudonymous **Reviewer ID**. Create a dataset in Scenarios. Import your synthetic scenarios or create demonstration data from Overview. The demonstration covers normal, incomplete, contradictory, repeated-question, embedded-instruction and unknown-assessment cases.
2. Preview imports. Fix structural errors; inspect content warnings separately. Duplicate and similarity warnings do not prohibit intentional research cases. Commit the import and use search/status/category filters and the review queue.
3. Review each exact scenario version. Approve, reject, edit manually, or request a local AI revision with feedback. Manual and AI edits create new candidates requiring human review. Original content and parent relationships remain available. Select a version to see its parent comparison with changed fields highlighted. AI revisions run independently of experiment AI control.
4. In Question bank, create/select an independent bank, then add, import or explicitly generate local question drafts. Review text, tags, applicability rules and origin; approve appropriate exact versions. Edits retain the stable question ID and bank and create a new unapproved version.
5. In Snapshots, freeze approved **latest** scenario versions and approved latest versions from the selected bank. If a newer candidate is pending, an older approved version is not silently substituted. An explicit **Experimental** bank snapshot may include technically valid unreviewed versions for development only, never rejected versions. Dataset approval requirements remain unchanged. Existing snapshots remain unchanged when reviews change; test-containing datasets are marked frozen.
6. Select a dataset snapshot, split, methods, generator models, bank snapshot where needed, settings and repetitions. Select **AI control: Yes/No** and, if enabled, a separate evaluator model. Queue the experiment. A fixed-bank run works without Ollama when AI control is off.
7. Follow persistent job progress. Inspect prompts, rules, retrieved IDs and scores, selected question version, effective settings, errors, partial text, model identity and timings. Cancellation closes in-flight generation streams when supported by the HTTP connection and retains partial records. Local Ollama may take time to release its computation after disconnection.
8. Review generated questions in **Evaluation**. Method/model identities are hidden by default in the manual-review form; order is randomized by a recorded seed. Review usefulness and contextual correctness independently, with explanation and supporting/conflicting context. Not assessed is an incomplete state. Save labels under the exact output ID/version. The same page can run a separate local evaluator on saved output versions without regenerating them.
9. Optionally assign another reviewer a subset, selecting **secondary**. Adjudication requires references to two reviewers' labels on the same output/version. Existing AI or human decisions are never overwritten; updates append records. Metrics use the latest adjudication, otherwise the designated primary human reviewer. Other judgments are hidden in a closed disclosure until requested.
10. Inspect Metrics and export experiment records or the whole workspace. Record which frozen inputs influenced prompt/rule/model choices using the influence log. Use test sets for final evaluation; logging test influence makes contamination visible, but does not undo it.

## Independent question banks and local generation

In **Question bank**, use **+ New bank** to name a collection (optional description), then select it in the bank selector. Add/import/edit/review actions affect only that bank. Edits create new versions in the same bank; exact duplicate text in another bank is allowed, while duplicates within the destination bank are rejected. Similar-but-distinct wording is retained with a near-duplicate warning. Tags remain descriptive and never execute applicability rules.

**Generate questions** opens a compact form with the existing installed-model selector, count (1–1000), reflection purposes and optional instructions. Purposes cover progress, understanding/control evidence, learning strategies, time/planning, obstacles, clarification, next steps and a neutral fallback. Both retrospective reflection and planning are requested. Only **Queue question generation** starts inference. Opening the form, choosing a bank/model or refreshing does not generate/download anything. One actual local request produces one question with `text`, `tags`, `conditions`, `priority`, `origin` and a strict schema. Conditions use supported `present`, `missing`, case-insensitive `contains`, numeric `compare` and canonical `control_assessment`; malformed/thinking-only answers, exact duplicates, invalid predicates and clear unsupported assumptions trigger bounded retries. Human review is still needed for semantic applicability and educational quality.

Question-generation jobs use their own defaults (temperature 0.4, 768 output tokens, context 4096, timeout 120 seconds, thinking disabled). Selected themes rotate with different item focuses and perspectives. Actual existing bank texts, including saved drafts, are reference data: at most `min(6000, num_ctx)` UTF-8 JSON bytes, prioritizing recent and theme-relevant questions, then rotating older texts. Long lists are a bounded selection; duplicate validation still checks the full destination bank. Duplicate retry feedback names the repeated text and requests a different reflection decision/action rather than cosmetic paraphrasing. Role boundaries and strict validation are preserved; the versioned small condition extensions are described below. Temperature and selected model are never changed automatically.

If a seed is supplied, the recorded attempt seed is `base + zero_based_item * 3 + zero_based_attempt`; null remains unset. Each explicit run/resume permits at most three attempts per unsaved item, at most `3 * remaining items` overall. Exhausted items are recorded and later planned items continue. Three consecutive exhausted items stop the run with a no-progress explanation. Saved drafts and progress commit atomically. Counts show requested, saved, failed and pending; an otherwise finished run with failed items is `completed_with_errors`, not full success. **Resume remaining work** retries only failed/pending item IDs, preserving successes even when an earlier slot failed. All attempt histories remain available. Transport/digest errors and cancellation stop promptly. The generator's model/digest remains pinned and independent of research/evaluator selections.

Generated questions start **awaiting review**. Bank status shows whether an eligible unconditional fallback exists for each review mode. In **Snapshots**, select the bank and choose **Approved only** (regular workflow) or explicitly **Experimental — unreviewed allowed, development only**. Experimental snapshots copy each included version's actual review status, exclude rejected questions, preserve bank configuration and content hash, and cannot be used for validation/test experiments. Later reviews do not modify frozen snapshots. In **Experiments**, select the specific named bank snapshot; fixed-bank/RAG use that snapshot, while constrained LLM uses none. Fixed-bank plus AI control off still requires no LLM. Condition IDs, metrics and exports retain snapshot ID, bank ID, review mode and hash so different snapshots are not silently treated as one condition.

For a generated question, expand **View generation prompt** to inspect the exact HTTPX-captured system/user messages, separate schema, installed tag/digest, effective settings and generation job/attempt IDs. Retries stay linked to the exact saved version via the successful attempt ID/response ID (one question per response). Original prompt text is never reconstructed; older questions without saved prompts show **Generation prompt not recorded**. Bank, question-version, generation-job and workspace exports include provenance outside question text/conditions. The research methods consume only supported question text/tags/rules, not generation instructions or traces.

Migration is automatic and idempotent: existing question versions receive the identity **Default question bank** (`bank_legacy_default`). IDs, version numbers and review histories remain unchanged. Existing frozen snapshots, content hashes and experiment references are not rewritten; legacy snapshots are identified as approved-only default-bank snapshots by an API/export identity mapping. Before this update, the live database was backed up to `data/research-before-banks-20261026-162245.sqlite3`. Audit results are in `docs/bank-migration-verification.json`.

Relevant APIs: `GET/POST /api/banks`, `GET /api/questions?bank_id=...`, `POST /api/banks/{id}/generate`, `POST /api/snapshots` with `bank_id`/`review_mode`, and `GET /api/banks/{id}/export`. Existing no-bank-ID question APIs default to the migrated bank for writes and preserve all-bank discovery for reads; the UI always supplies the selected bank.

## Scenario import formats

Ready-to-use examples: `templates/scenarios.json`, `scenarios.jsonl`, `scenarios.csv`, `csv-mapping.json`; question suggestions: `templates/questions.json`. Regenerate them from the root with `.venv/Scripts/python.exe -m scripts.make_templates` (or the corresponding POSIX executable).

JSON is an array of `ScenarioRow` objects (also accepts an object with a `scenarios` array). JSONL has one object per line. CSV has a header, one scenario per row, and UTF-8 encoding; a BOM is accepted. Limits: 10 MB and 5,000 rows per import. JSON/CSV parse errors and structural errors block the whole commit. Preview reports row numbers (CSV data begins on row 2). Duplicate/similarity/content warnings permit import. JSONL blank lines are errors, apart from the ordinary final newline.

```json
[
  {
    "scenario_id": "case-001",
    "family_id": "family-001",
    "split": "development",
    "tags": ["incomplete"],
    "synthetic_origin": "Manually constructed synthetic case",
    "inputs": {
      "learning_goal": "Explain equivalent fractions",
      "planned_activity": "Solve six problems",
      "progress": {"description": null, "planned_units": 6, "completed_units": null, "unit": "problems"},
      "planned_time": {"value": 20, "unit": "minutes"},
      "reported_time": null,
      "control_results": [{"question": "Is 2/4 equal to 1/2?", "student_answer": "Yes", "reference_answer": "Yes", "recorded_assessment": null, "ai_inferred_assessment": null}],
      "student_note": "I have not recorded my progress.",
      "previous_question": null
    },
    "research_labels": {},
    "evaluation_notes": ""
  }
]
```

All input fields are optional; omitted values are stored as `null`. Missing progress or assessment is never treated as zero, failure or success. Empty lists mean no supplied records, not evidence of correctness. Time objects require a finite numeric value and an explicit unit: `seconds`, `minutes`, or `hours`. Progress counts must also be finite JSON numbers; booleans and text numbers are structural errors. Progress units are a free-text description. Negative values and completed > planned are content warnings, not prohibited research cases. Contradictory prose cannot be detected comprehensively; reviewers must inspect it. Structural fields reject unknown keys at every model-input level.

Research metadata belongs outside `inputs`. Allowed row metadata: scenario/family IDs (optional/generated), split (`development`, `validation`, `test`), tags, synthetic origin, research labels and evaluation notes. Imported rows cannot grant themselves approval. Family splits are preserved globally across the workspace and across revisions. Existing scenario IDs are rejected by bulk import; use a revision endpoint/UI for edits. Reimporting exported data into a new workspace preserves IDs; copying it into the same workspace requires new IDs.

CSV nested objects/arrays use JSON inside standard quoted cells. For example, a `progress` object inside a cell is `"{""planned_units"":6,""completed_units"":null}"`. The bundled CSV uses an `inputs` JSON-object column. Alternatively, use headers such as `inputs.learning_goal`, `inputs.progress`, `tags`, `split`; dotted scalar fields such as `inputs.progress.completed_units` are also supported. An empty cell is unknown/omitted. Numeric nested leaves use JSON numbers; quoted text `"null"` is not a number. All field mappings are **target field → source column**, e.g. `{"inputs.learning_goal":"Goal","inputs.progress":"Progress"}`. An empty mapping uses headers as target paths; a nonempty mapping uses only listed columns. IDs and splits are strings, tags are a JSON array, and research labels are a JSON object.

Dataset export offers JSON, JSONL and CSV. The Scenarios **Export JSON** action includes a `scenarios` array of latest importable rows plus a separate `generation_provenance` archive indexed by exact scenario-version IDs. JSONL/CSV remain plain interchange rows; the API's default JSON row format remains available without `include_provenance=true`. Importing the archive reads its scenario rows, without asserting imported provenance as a newly observed request. Use full workspace export for all history/reviews. CSV values are preserved exactly for research round trips: do not open untrusted CSV text in a spreadsheet that executes cell formulas; JSON is preferable for research interchange.

## Methods and inspection

- **Fixed bank, `conditions-v2-normalized-comparisons`:** no LLM. Match all predicates, then priority descending, normalized specificity descending and stable question ID ascending. Presence/missing parent and child paths share a root score; presence already implied by a comparison adds no score. Numeric comparisons are unique clauses. With no specific match choose an eligible unconditional fallback; otherwise record failure. Winning priority, normalized specificity, candidate IDs and fallback reasons are retained. No random rotation masks weak rules.
- **RAG, `reflection-v1` + `tfidf-values-v2-applicable`:** retain TF-IDF cosine but index question text only; query actual student text values, not JSON keys, tags or numeric time templates. Generic stop words are removed. Applicability predicates determine retrieval eligibility; fixed-bank priority does not rank retrieval. Scores below 0.12 are excluded; no relevant match is explicit. Scores are lexical diagnostics, not evidence of semantic suitability. Exact version IDs, scores, query text, threshold and policy are retained. Approved versus experimental prompt fields remain separate and only allowed Inputs enter the generator.
- **Constrained LLM, `reflection-v1`:** use the same scenario inputs and generation constraints, without retrieval or bank content.

Both generative methods request exactly one short English reflection question: clear, relevant, answerable, non-coercive, preserving agency, avoiding unsupported assumptions and repeated questions. Format checks detect empty output, multiple question marks, wrong ending, >40 words, multiline output, and exact prior-question repetition. They do **not** establish English-language or semantic correctness: the rubric requires review. Invalid/empty outputs and original responses remain in reporting.

Question-generation prompts use `schema.prompt_inputs` as a nested allow-list. Reviewer labels, feedback, evaluation notes, family IDs, split, categories and future outcomes never enter question-generation prompts. AI-inferred control assessments are stored separately and excluded from observed context. Recorded assessments remain evidence about what was recorded, not guaranteed truth. Synthetic generation/revision receives its own role-specific prompt; revision additionally receives reviewer feedback. Protocol & records exposes prompt/rule text and versions. Changing those constants changes future runs only. Record the influencing snapshot and decision before comparing versions.

Repetitions use the same settings except seed = base seed + zero-based repetition index, where supplied. The condition queue is randomized with `order_seed` (default 42) for balanced ordering in expectation. These seeds are retained; exact determinism is not promised across hardware, Ollama versions, model backends or scheduling. Fixed runs do not gain a model parameter count by being repeated.

## Evaluation and metric definitions

In **Evaluation**, select an existing experiment, optional method/generator/category subset, and existing AI/human assessment filters. The eligible/skipped count is read-only; **Evaluate with local model** explicitly queues inference using a separate installed evaluator and explicit settings. Existing exact-version AI assessments are skipped unless **Re-evaluate** is selected. Empty/invalid/truncated/failed questions are skipped as execution failures, with reasons, not assigned fictional quality labels. Jobs support cancellation, partial preservation, resume and export through the existing queue. Re-evaluation appends a new AI label; the latest exact-version AI label is active, while prior AI assessments and human labels remain unchanged. Resume also recovers a label committed just before a lost progress checkpoint.

The evaluator reuses the independent usefulness/correctness rubric (`rubric-v2-evidence`) with strict required Yes/No criteria and evidence explanations. Missing, malformed, output-limited or failed judgments never default to Yes. Generator identity is omitted from the judgment prompt. Same generator/evaluator tag or digest is allowed intentionally and recorded as a bias flag. Actual HTTP request, rubric/schema, raw response, model/digest, effective settings, validation outcome and duration are retained in assessment records and exports. Inline and later saved-output evaluation use the same implementation.

**Run evaluator calibration** executes six controlled development examples outside research labels/metrics. Reported differences from development expectations are not measured accuracy; the generic safe example can reveal criterion conflation. Human reference coverage and paired exact-version labels are still required for evaluator agreement. With no human labels, human quality/end-to-end acceptance and macro-F1 show **Not assessed** rather than measured zeros. Metrics separate processing finished, valid output counts, failure reasons, assessed quality, review coverage and end-to-end acceptance. Fixed-selection and RAG-retrieval concentration are diagnostics, not proof of failure or a winning model. Inline evaluation time and later saved-output evaluation time are separate; preflight/calibration are excluded. Peak memory remains not measured.

### Small applicability extensions and diagnostics

Existing conditions remain valid. `compare` is an optional array of `{left, op, right}` with `eq`, `gt`, `gte`, `lt`, `lte`. Only `progress.completed_units` versus `progress.planned_units`, and `reported_time.value` versus `planned_time.value` are supported. Missing/non-numeric values never match. Progress needs its shared unit; time values are converted between seconds/minutes/hours before comparison. Example completion: `{"compare":[{"left":"progress.completed_units","op":"gte","right":"progress.planned_units"}]}`. `control_assessment:"incorrect"` or `"correct"` requires that canonical recorded value plus an actual control question and student answer; free-text functionality descriptions and inferred assessments do not count. These rules do not detect arbitrary semantic contradictions, pressure, emotions or completed corrective work.

In Question bank, expand **Bank applicability and selection diagnostics**, optionally choose an exact bank snapshot and a development dataset snapshot, then **Inspect applicability**. It reports duplicates, lexical near-duplicates, fallback rules, determinable unreachable/shadowed rules, actual selection frequencies, unused questions and winning reasons. Nothing is generated or changed; uniform selection is not a goal.

### Planned synthetic scenario generation

Under **Generate locally**, choose ICT topics, variations and total. The balanced plan cycles topics within each variation (30 across five topics and six variations covers all combinations); a custom distribution may specify rows with topic, variation and count. Optional `family_id` on rows groups deliberate variants; unrelated new cases otherwise receive separate families, and revisions preserve their existing family. Every request names its topic, variation and concrete activity focus. Bounded reference summaries discourage repeating activities and time templates. Clear topic mismatch, incompatible completion evidence, requested-missing violations and exact duplicate Inputs trigger at most three attempts per item. Near-duplicates and ambiguous semantic inconsistencies remain visible warnings for human review.

For planned complete/partial variations, the actual output schema specifies a small set of coherent fictional count/unit pairs and requires real fictional control question/answer records where understanding/incorrectness is requested. These are pre-request case constraints, not post-response fact repairs. Explicitly requested missing fields remain null. Technical functionality descriptions are warned about as non-assessment evidence; `previous_question` must be a reflection question or null. Contradictions are labeled intentional when requested; the app does not claim a general contradiction detector. Generation summaries separate assigned variations from observed features/topic coverage and include duplicate rejections and unresolved warnings. Generated drafts always await human review.

Historical snapshots, outputs, prompts and labels are not rewritten. New experiments record changed rule/retrieval/rubric identities, modes and digests in condition IDs. Resume is blocked if research implementation versions changed; create a new configuration. Model/digest drift remains an explicit error. After updating source, build with `cd frontend; npm.cmd run build`, then restart the single backend from the repository root with `.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000`. Refreshing the browser alone cannot update imported backend prompts.

Usefulness: meaningful reflection, clear/answerable/relevant, agency without pressure or judgment. Contextual correctness: accurate use of available information, no invented performance/emotions/causes/circumstances, appropriate treatment of unknowns and contradictions. Each criterion stores `Yes`, `No`, or `null` (Not assessed), a short explanation and context. Null is excluded from binary evaluation comparisons and explicitly counted through review coverage.

Question-quality reporting separates human-reference and AI results, with overall, category and method/model breakdowns:

- Useful/correct rates = Yes / assessed labels for that criterion.
- Both rate = Yes on both / outputs assessed on both.
- End-to-end acceptance = valid, completed questions with both Yes / **all attempted cases**, including generation failures and unreviewed attempts. This is evidence of accepted outputs so far, not an assumption that unreviewed questions are poor.
- Planned and not-yet-attempted counts are separate. Failure/status counts include empty/invalid outputs, failures, timeouts, cancellations and interruptions; evaluator failures are separate from generation failures. A job marked completed can contain failed cases: it means queue execution finished.
- Overlapping category tags can cause category totals to overlap. Review coverage is assessed / attempted cases. Human reference follows adjudication if present, otherwise the primary reviewer's latest record; secondary reviews are used for disagreement analysis.

Evaluator accuracy is computed only from AI/human labels on the **same output ID and version**, separately per criterion. Matrix rows are human truth, columns AI prediction. For each fixed class Yes and No: precision = TP/(TP+FP), recall = TP/(TP+FN), F1 = 2PR/(P+R). Undefined divisions produce 0. Macro-F1 is the unweighted mean of the **two fixed class F1s**, including an absent class as 0. Support and predicted class counts are exported; absent classes and fewer than 30 pairs trigger an interpretation caution (30 is a display caution, not a statistical sufficiency claim). No pairs displays “Not available: human reference labels required”. F1 measures agreement with the chosen human reference; it does not directly measure question quality, feasibility, learning benefit or ethical validity.

Feasibility includes separate generation and evaluator timing, active worker experiment duration (excluding queue/paused time), completed-case throughput, status/failure breakdowns, available Ollama load/runtime information, hardware/runtime notes and model configuration. Timing includes local orchestration overhead; first generation may include model load. There is no automatic warm-up. Process/GPU peak memory is not reliably measured: **Not measured**. File size is not memory usage. Optional quality, latency and memory thresholds are stored with the experiment; no universal thresholds or automatic winner are supplied. Quality thresholds use the human both-assessed rate; inspect coverage before interpreting them. Memory thresholds remain unassessable. Later threshold changes require a researcher/reason and are flagged retrospective.

## Persistence, jobs, recovery and deletion

SQLite is stored under `data/`, WAL enabled, with transactional imports, revisions and job creation. The repository uses a single transactional writer in this process. Run **one Uvicorn process/worker**; do not use `--workers` or `--reload` during experiments. This is a local single-researcher environment, not a multi-user server.

In **Experiments → Persistent jobs**, **Remove from queue** immediately terminates a queued job and cancels its pending worker task. Failed, interrupted and cancelled jobs offer **Terminate job**. Terminated jobs cannot be resumed and are hidden by default; enable **Show terminated jobs** to inspect/export retained results, drafts, errors and execution records. Termination is not deletion. Cancel running jobs and wait for them to stop before terminating them. Normal cancellation remains resumable; cancelling a still-queued job also takes effect immediately. Worker state checks prevent removed entries from starting afterward, and termination persists across restarts.

Use **Archive job** on a finished/stopped job to hide it from the main Experiments list and bank progress cards without changing its execution status or deleting anything. **Archived jobs** opens retained history, including archived terminated jobs; **Find job** searches name, ID, kind and status. Inspect/export remains available. **Restore job** returns it to the main list (use Show terminated jobs for restored terminated entries). Archive state persists across reloads/restarts. Explicitly resuming an archived resumable job also restores it. Running or queued jobs cannot be archived.

All inference and batch execution runs in a background worker, never a long HTTP experiment request. UI polling shows durable progress. Output prompts are saved before inference and completed generation before evaluation. On startup, queued/running jobs become **interrupted**; choose Resume explicitly. Finalized outputs are retained, and generation completed before interrupted AI evaluation is reused. An interrupted/cancelled unfinished generation resumes with an incremented output version and an attempt-history entry. Output labels always name the exact generated version. Failed/invalid/finalized cases are not silently retried on Resume: launch a new experiment for a comparable rerun. Active duration is checkpointed at job completion; a hard process kill can undercount the last uncheckpointed worker interval. Per-output timestamps, model runtime and partial results remain available. Streamed partial text is retained on timeout/cancellation, but a hard OS kill can lose tokens not yet saved by the provider boundary.

Scenario jobs save each candidate and progress in one transaction. AI-generated candidates always await review. Each item gets one request and at most two corrective retries for invalid JSON/schema output. Exhausting those three attempts fails the job with item number, validation paths/types and retained-draft count. Transport, model identity, unsupported schema/provider, timeout and cancellation failures are not blindly retried. Already completed drafts survive; explicit Resume attempts only the remaining sequence with a fresh bounded retry budget. Scenario revision requests are based on the exact selected parent even if a newer branch exists; all branches receive unique monotonic version numbers.

### Synthetic scenario output contract

The `synthetic-inputs-v5-planned` generation/revision path sends the JSON schema derived from `Inputs` as Ollama's **`format` object**, following the [structured-output interface](https://docs.ollama.com/capabilities/structured-outputs). It does not place a schema object into scenario content or rely on `format: "json"` alone. The eight allowed fields are `learning_goal`, `planned_activity`, `progress`, `planned_time`, `reported_time`, `control_results`, `student_note`, `previous_question`. Category, split, job sequence and reviewer feedback are request/provenance context; saved scenario tags/split remain outside `inputs`. No output wrapper is extracted, and unknown keys are never silently removed. Unsupported schema constraints fail visibly; there is no automatic downgrade to unconstrained output.

New AI generation and revision explicitly require ICT learning goals/activities: programming/algorithms, databases/SQL, web/APIs, software testing, Git/version control, networking/security or software design/requirements. ## Responsible AI decisions and limits

Synthetic data is the default; importing identifiable students is discouraged. Avoid demographic attributes unless a separately justified research protocol requires them. The browser and API display/store data; SQLite persists it; the local Ollama process receives allowed prompts. Runtime application assets are local and no external fonts, analytics or AI API calls are used. Setup downloads software packages, and manually installing model files requires network access, but research inference does not.

The API binds to loopback by default, rejects external host/origin headers, and disables outbound provider proxies/redirects. Docker deployments bind internally and publish only to host loopback as described above. It is not an authenticated or encrypted multi-user service; other processes/users with access to the computer may access local data. The provider trusts the configured local Ollama process to report remote-model metadata correctly. A malicious/reconfigured local service or manually forwarding proxy is outside this boundary. Prompt injection remains a model robustness risk; quoted JSON, system constraints, allow-listed inputs and embedded-instruction cases support testing, not a guarantee of immunity.

AI explanations are judgments, never proof. Synthetic generation, question generation and evaluation roles are separate, but reusing weights can correlate errors. Experiments record models for each role and flag overlap across snapshot scenario generation/revision, question generation and AI evaluation. Review questionable synthetic construction separately from intentional robustness cases. Human labels can also disagree; second-review subsets and adjudication document this. Review category coverage and individual failures rather than relying on averages. No result from this local synthetic environment establishes effectiveness with real students, improved learning, legal compliance or ethical validity.
